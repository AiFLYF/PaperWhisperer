# Localisation

PaperWhisperer speaks **Chinese and English**, switchable in the header, and
**Chinese is the default**. This document is the reference for how that works
and for the rules a new string has to follow.

---

## 1. The default, and why

`DEFAULT_LOCALE` is `zh-CN`.

A reader who opens the product without choosing a language is served Chinese.
The product is Chinese-first and the backend's own error prose is Chinese, so
an English shell over Chinese errors is a worse first impression than either
language alone. English is a **first-class supported mode**, not a consolation
fallback: every key in the catalogue has both languages, and the switcher is in
the template.

### The resolution order

`resolveInitialLocale()` in `templates/static/js/i18n.js`:

| Order | Source | Notes |
|---|---|---|
| 1 | Stored preference | An **explicit** choice. Consulted first and never second-guessed. |
| 2 | Browser preference | `navigator.languages`, then `navigator.language`. Chooses only the *starting* language. |
| 3 | `DEFAULT_LOCALE` | `zh-CN`. |

The order is the whole design. Detection can move the starting language; it can
never move a Chinese-capable browser to English, and it never overrides a choice
the reader has already made.

### Tag mapping

`normalizeLocale()` returns a supported locale or `null` — it never guesses, so
the caller can fall back *deliberately* rather than by accident.

| Input | Result | Why |
|---|---|---|
| `zh`, `zh-CN`, `zh-Hans`, `zh-SG` | `zh-CN` | Simplified Chinese, the only Chinese shipped. |
| `zh-TW`, `zh-HK`, `zh-MO`, `zh-Hant`, `zh-Hant-HK` | `zh-CN` | **Deliberate.** There is no traditional catalogue, so returning `null` would drop the reader onto detection and possibly onto a language they did not ask for. Simplified is the lesser surprise. |
| `en`, `en-GB`, `en-US` | `en` | |
| `fr`, `ja`, `de`, `ko`, `yue`, … | `null` | Unsupported → the default applies. |
| `''`, `null`, non-strings | `null` | |

## 2. Storage, and why it cannot take the page down

The preference is written to `localStorage` under `paperwhisperer-locale`.

Every access goes through `safeStorage()`, which touches the API as a probe and
returns `null` on any throw. This matters because in private-browsing modes and
under a disabled-storage policy, **`localStorage` throws on access and on write
rather than returning `null`** — Safari's private mode is the canonical case. A
bare `localStorage.getItem` would throw out of `resolveInitialLocale` and take
the entry module's initialisation with it, so a browser privacy setting would
present as a broken application.

When storage is unusable the reader loses the *preference*, not the interface:
detection and the default both work without storage, so the language switcher
still functions for the current page view.

A stored value is only honoured when `normalizeLocale` accepts it. A value
naming a locale this build does not ship is discarded, because **a preference
stored wrongly is worse than no preference** — `localStorage` holds whatever a
previous build, a hand edit or a half-written write left there.

## 3. The catalogue

`templates/static/js/i18n.js`. Plain data and a small runtime; no framework, no
build step, no npm.

```js
export const CATALOGUE = { 'zh-CN': { 'key': '…' }, en: { 'key': '…' } };
```

- **Flat, dotted keys.** One property read per lookup, and a missing key is a
  one-line set difference in a test rather than a deep `undefined`.
- **One copy of each sentence.** The Chinese values that already existed as
  module-level constants in `config.js` are *reused*, not retyped — the `zh-CN`
  table points at them. A wording fix in `config.js` cannot leave a stale
  duplicate behind in the catalogue.
- **The old English blocks are the English locale's values.** `SECTION_EMPTY_TEXT`,
  `ANSWER_MODE_LABELS` and their neighbours were untranslated defaults; they are
  now `en` values with new Chinese entries beside them.

### Adding a string

```js
// i18n.js, both tables
'export.fact.method': EXPORT_FACT_FIELD_LABELS.method,   // zh — reuses config.js
'export.fact.method': 'Method',                           // en
```

```js
// the module
updateStatus(t('status.waiting'), 'idle');
```

Rules:

1. **A module that builds a string by concatenating a bare literal is not
   migrated**, however small. `updateStatus('Copied')` is as much a defect as
   `updateStatus('Analyzing...')`.
2. **No literals in a user-visible sink.** The test in `tests/test_i18n.py`
   enforces this for the modules it lists. Extend the list as modules land.
3. **Keys are namespaced by area** (`upload.`, `evidence.`, `export.`, …).
4. **Interpolation goes through `{name}` placeholders**, never string
   concatenation:

   ```js
   t('evidence.characters', { start: snippet.start, end: snippet.end })
   ```

5. **A missing key renders as the key.** `t()` falls back to the default locale
   and then to the dotted key itself, so a miss is visible in review instead of
   being a silently blank button.

### Numbers, dates and units

`formatNumber()`, `formatDateTime()` and `formatFileSize()` wrap `Intl`. A
hard-coded `"4 pages"` is a localisation bug: `en` groups thousands, `zh-CN`
formats dates differently, and neither is negotiable. Any number a reader sees
goes through one of these rather than through `String(n)`.

## 4. Errors: driven by `code`, never by the server's prose

### The problem

`build_error_payload` in `paperwhisperer/core/errors.py` returns:

```json
{ "error": "会话不存在或已过期。", "code": "session_not_found", "timestamp": "…" }
```

The `error` field is **always Chinese**. It carries no `lang` attribute and no
declared language. So a reader who explicitly switches to English gets an
English interface, and — if the prose is surfaced as the headline — an English
page with a Chinese sentence stranded in it. That is worse than either language
alone.

### The split

The backend sends a stable, language-neutral `code` beside the prose. So:

| Concern | Owner | Question it answers |
|---|---|---|
| Is retrying worthwhile? | `ERROR_PRESENTATIONS` in `config.js` | `retryable` / `terminal` / `unreachable` |
| What do I say? | `ERROR_CATALOGUE` in `i18n.js` | the reader-facing `title` / `message` / `hint`, per language |

`runtime.js`'s `normalizeFailure()` is the seam. It takes `kind` from
`config.js` and copy from `errorPresentation(code, serverMessage)`, which
returns:

```js
{ code, known, title, message, hint, serverDetail }
```

`serverDetail` is the server's own sentence, **carried but never used as the
headline** — its language is not assumed to be the reader's, and a caller may
show it beside our sentence when it adds something or drop it when it does not.

### An unrecognised code

A `code` this build has never heard of gets the `error.unknown.*` copy, in the
reader's language, and `known: false`. It does **not** fall back to the Chinese
server prose, and it does not get an invented sentence: saying "this version
does not know this code" is true, is actionable for an operator, and is in the
reader's language.

`tests/test_i18n.py` asserts that every code in `ERROR_PRESENTATIONS` has copy
in both languages, so the two tables cannot drift apart.

## 5. Interface language ≠ document language

These are **two separate axes**, and the second is never derived from the first.

The corpus is Chinese and English papers, frequently mixed inside one file. A
reader who switches the interface to English is still reading a Chinese paper.
Labelling that paper's sections "Summary" while translating its headings would
relabel the **document**, not the tool.

So:

- `<html lang>` describes **the interface**. It is set to the UI locale.
- A content region's `lang` describes **what is inside it**, and is derived
  from that text by `documentLocale()`.

```js
markDocumentLanguage(container, documentText);   // never markDocumentLanguage(c, getLocale())
```

`documentLocale()` classifies by CJK character **ratio** (threshold 0.2), not
presence. A handful of ideographs in an English abstract — a cited paper title,
a Chinese author name — must not flip a document's language.

A `lang` that disagrees with the words it wraps is **worse than no `lang`**: it
makes a screen reader pronounce Chinese with English phonetics. An
indeterminate region is left unlabelled rather than labelled wrongly.

### What else depends on `lang`

- `dir` is set from the locale, so adding a right-to-left language is a
  catalogue entry and not a stylesheet change. Both shipped locales are LTR.
- `data-ui-lang` is set on `<html>` as a stylesheet hook. It means "the
  interface is in this language", which is the question font stacks and
  letter-spacing need answered.
- `aria-label`s are translated through `data-i18n-attr`, so a control's visible
  text and its accessible name never disagree.

## 6. The switcher

`#languageSwitcher` in `templates/index.html`, inside `.nav-actions`.

A **radiogroup**, not a toggle. With two languages a toggle hides which one is
active while costing two tab stops to undo. `role="radiogroup"` with
`role="radio"` children is also what makes a screen reader announce "2 of 2"
rather than reading two unrelated buttons.

- **Keyboard**: one tab stop for the group; `←`/`→`/`↑`/`↓` move within it
  (roving `tabindex`); `Space`/`Enter` select. Implemented in
  `handleSwitcherKeydown()`.
- **Announces its state**: `aria-checked` on every option.
- **Not colour-only**: the selected state is carried by `aria-checked` *and* by
  `data-selected`, which the stylesheet renders as an inset ring plus a heavier
  weight — border, ring and weight, not background colour alone, so it survives
  forced-colours mode.
- **Endonyms**: each option names its own language in that language (`中文`,
  `English`), so the control stays readable whichever locale is active.

Wiring: `initializeI18n()` is called at the **top** of `main.js`'s
`initialize()`, before the theme, the status chip and every feature module, so
the first paint is already in the reader's language.

`i18n.js` is reached through `main.js` as an ordinary import. The template must
keep **exactly one** `<script type="module">`; adding a second would break both
`tools/check_frontend.py` and the existing wiring test.

### Re-rendering on a switch

Static markup is translated by `translateStaticMarkup()`. Anything a module
renders is produced at render time, so a locale change must be followed by a
re-render. Modules subscribe:

```js
onLocaleChange(() => renderResultView());
```

`i18n.js` deliberately does not import feature modules to do this itself — that
would build an import cycle through every one of them. It exposes both a
callback list and a `paperwhisperer:localechange` DOM event.

## 7. Layout of the code

| File | Role |
|---|---|
| `templates/static/js/i18n.js` | The catalogue and the switching mechanism. Imports `config.js` and nothing else, so it sits below every feature module in the graph. |
| `templates/index.html` | `<html lang>`, the switcher markup, `data-i18n` / `data-i18n-attr`. |
| `templates/static/js/config.js` | `ERROR_PRESENTATIONS` — **policy only** (`kind`). Plus the Chinese constants the catalogue reuses. |
| `templates/static/js/runtime.js` | `normalizeFailure()` — the seam joining policy to copy. |

## 8. What is verified, and what is not

`tests/test_i18n.py` runs the detection, fallback, storage, lookup, error and
document-language rules **against the real module** in Node. A source grep
cannot honestly assert that an unsupported browser language falls back to
Chinese — it would pass just as happily against a `DEFAULT_LOCALE` of `'en'`,
which is the exact bug the default exists to catch.

Static markup translation is exercised against a minimal DOM stub, which proves
the lookup runs, the text is replaced and the attribute keys are written.

**Not verified here, and needing a manual check in a browser:**

1. That the switcher *looks* right in both languages — in particular that the
   Chinese and English labels fit the control at the smallest breakpoint.
2. That the arrow-key roving focus lands where it should, and that the visible
   focus ring survives forced-colours mode.
3. That a screen reader announces "2 of 2" for the group and the correct option.
4. Line breaking and text expansion in the header, where English strings are
   considerably longer than the Chinese ones they replaced.
5. A mixed Chinese/English document's rendering, beyond the `lang`
   classification that `documentLocale()` performs.

These are listed rather than asserted because a test that cannot fail on the
defect it names is worse than no test.

## 9. Known gaps and what resists localisation

- **Modules not yet migrated.** The catalogue, the switcher and the error
  surface are complete; a number of feature modules still hold bare literals and
  await migration. `tests/test_i18n.py` scopes its "no bare literals"
  assertion to the modules actually migrated, and the list should be widened as
  the rest land. A test scoped wider would fail for work that has not landed
  yet, which trains the suite to be ignored.
- **The stylesheet.** The switcher's rules live in a namespaced `<style>` block
  in `index.html` and should be folded into `chrome.css` by the design owner.
- **The backend's prose stays Chinese.** Changing it is a `paperwhisperer/`
  concern and out of scope here. The client no longer depends on it.
- **Server-supplied content is not translated.** Suggested questions, action
  labels, paper titles, abstracts and model-generated section text are content,
  not interface copy, and are rendered verbatim. Translating them would mean
  translating the analysis, which is the backend's business.
- **Direct-quotation marks are a locale decision, not a lookup.**
  `DIRECT_QUOTE_OPEN_MARK` / `DIRECT_QUOTE_CLOSE_MARK` in `config.js` are
  `“ ”`, and `export.js` hard-codes the same pair outside the constants. Both
  shipped locales use them, so the value is currently correct for both — but the
  release gate in `tests/test_frontend_evidence.py` treats the mark
  constants as the thing a paraphrase may never name, so a locale that does not
  use `“ ”` would need that decision settled deliberately rather than by
  changing a string.
